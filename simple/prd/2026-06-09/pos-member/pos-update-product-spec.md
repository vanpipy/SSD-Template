## 2. 详细需求

### 2.1 静默下载

| 项目 | 说明 |
|------|------|
| **触发时机** | App已启动状态下，后台检测到有新版本发布 |
| **用户感知** | 完全无感知，不弹窗、不通知、不阻断当前操作 |
| **下载行为** | 后台异步下载全量APK更新包，不阻塞UI线程 |
| **网络要求** | Wi-Fi环境优先；4G/5G环境下提示"正在使用移动网络下载"，不强制阻断 |
| **下载完成** | 更新包存于应用私有目录，标记`pendingUpdate=true` |
| **异常处理** | 下载中断（网络断开/存储不足）：下次启动时重新检测并下载 |

**技术约束**：
- 全量更新，不做差分更新（避免补丁包兼容性问题）
- APK包下载后需校验 MD5，防止传输损坏
- 下载路径：`/data/data/{packageName}/update/` 应用私有目录

### 2.2 触发自动更新（强制更新）

| 项目 | 说明 |
|------|------|
| **触发时机** | App下次冷启动时，检测到`pendingUpdate=true`且版本号匹配 |
| **策略类型** | 强制更新（用户不可跳过，不可推迟） |
| **检测逻辑** | 启动后 → 读取本地`pendingUpdate`标记 → 校验APK完整性 → 触发更新流程 |
| **阻断行为** | 在展示更新页面前，不加载任何业务界面；更新完成之前无法使用App |
| **异常场景** | 若`pendingUpdate`标记存在但APK文件丢失 → 清除标记，恢复启动至登录页 |

**为什么选择强制更新？**
- 移动收银APP涉及支付、库存等核心业务，版本强一致性避免后台接口兼容问题
- PDA设备为门店专用终端，非个人手机，可接受强制行为
- 若后续需要弱化，可在后台配置`updatePolicy`字段动态切换策略

### 2.3 全量更新（不做差分）

| 项目 | 说明 |
|------|------|
| **更新方式** | 全量APK安装，不做增量/差分更新 |
| **原因** | ① 差分补丁在PDA厂商定制ROM上兼容性差 ② 门店终端Wi-Fi环境稳定，传输成本可接受 ③ 全量更新可同时完成数据库迁移、配置覆盖等操作 |
| **更新包大小** | 典型值 60-120MB（含扫码引擎、数据库迁移脚本、资源文件等） |
| **进度粒度** | 以百分比（0-100%）为单位，配合状态文案展示 |

### 2.4 更新中页面

| 项目 | 说明 |
|------|------|
| **展示内容** | ① 标题："系统更新中" ② 新版本号/旧版本号 ③ 更新内容列表（4-6条） ④ 进度条（百分比） ⑤ 状态文案 |
| **进度粒度** | 百分比进度 + 已安装量（MB/总MB） + 状态文案 |
| **状态文案序列** | 正在准备更新环境 → 正在安装核心组件 → 正在更新数据库结构 → 正在升级扫码引擎 → 正在优化配置文件 → 正在校验文件完整性 → 即将完成 |
| **交互** | 仅展示，无用户操作，无"取消"按钮（强制更新不可打断） |
| **错误处理** | 安装过程中出错 → 转至更新失败页面 |

### 2.5 更新完成 → 自动跳转登录页

| 项目 | 说明 |
|------|------|
| **停留时间** | 更新完成页展示 3 秒后自动跳转 |
| **展示内容** | ① 绿色对勾图标 + "更新完成" ② 新版本号 ③ 倒计时文字 |
| **跳转目标** | App登录页面（若已登录且令牌有效，直接进入主页） |
| **自动行为** | 3秒倒计时结束后自动执行跳转，无需用户操作 |
| **异常处理** | 跳转失败（页面卡住）：保留"重试跳转"兜底 |

### 2.6 更新失败

| 项目 | 说明 |
|------|------|
| **触发条件** | APK校验失败、安装过程异常、存储空间不足、系统版本不兼容 |
| **展示内容** | ① 红色错误图标 + "更新失败" ② 错误码（如 E-2003） ③ 错误原因描述 ④ 技术支持联系方式 ⑤ 已上报提示 |
| **用户操作** | ① **重试更新**：重新进入更新流程 ② **取消**：返回App，但每次启动仍会检测到待更新版本并重新触发 |
| **上报机制** | 更新失败后自动将错误信息上报至运维中台，包含：设备ID、错误码、错误堆栈、当前版本、目标版本、网络状态、剩余存储空间 |
| **联系方式** | 显示服务热线 + 门店运维人员指引，供用户线下求助 |
| **取消后的行为** | 取消后返回App，但后台保留`pendingUpdate`标记。下次重新启动仍会触发更新。用户无法永久跳过（除非联系运维降级） |

## 4. 界面状态定义

| 状态 | 触发条件 | 页面元素 | 用户操作 |
|------|---------|---------|---------|
| **更新就绪** | 启动时检测到待安装更新包 | 版本标签、更新日志、"开始更新"按钮 | 点击开始更新（不可跳过） |
| **更新中** | 用户点击"开始更新"后 | 进度条、进度百分比/MB、状态文案、更新日志 | 无操作，仅查看 |
| **更新完成** | 安装成功 | 绿色对勾、版本号、3秒倒计时 | 自动跳转，无需操作 |
| **更新失败** | 安装过程异常 | 红色叉号、错误码、错误原因、联系方式、已上报标签 | 重试 / 取消 |

## 5. 后台配置接口规范

后台需提供版本更新配置接口，客户端启动时请求：

**请求**：`GET /api/app/version/check`

**响应参数**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `latestVersion` | string | 最新版本号（如 "2.0.0"） |
| `currentVersion` | string | 当前版本号 |
| `minimumRequiredVersion` | string | 最低允许版本（低于此版本强制更新） |
| `updatePolicy` | object | 更新策略 |
| `updatePolicy.type` | string | `"forced"` / `"optional"` / `"silent"` |
| `updatePolicy.installStrategy` | string | `"on_next_launch"`（下次启动安装） |
| `downloadUrl` | string | APK下载地址 |
| `packageSize` | number | 更新包大小（字节） |
| `md5` | string | APK文件MD5校验值 |
| `releaseNotes` | string[] | 更新内容列表 |
| `grayRelease` | object | 灰度发布配置 |
| `grayRelease.enabled` | boolean | 是否启用量发布 |
| `grayRelease.percentage` | number | 灰度比例（1-100） |
| `grayRelease.strategy` | string | 灰度策略：`"deviceIdHash"` |

## 6. 失败上报数据规范

当更新失败时，客户端自动向中台上报以下数据：

**接口**：`POST /api/app/update/report`

| 字段 | 类型 | 示例 |
|------|------|------|
| `deviceId` | string | "PDA-20230521-001" |
| `errorCode` | string | "E-2003" |
| `errorMessage` | string | "APK文件MD5校验失败" |
| `errorStack` | string | 异常堆栈（可选） |
| `currentVersion` | string | "1.8.5" |
| `targetVersion` | string | "2.0.0" |
| `networkType` | string | "WIFI" / "4G" / "5G" |
| `freeStorage` | number | 剩余存储空间（字节） |
| `updatePackageSize` | number | 更新包大小（字节） |
| `timestamp` | string | "2026-05-23T10:30:00+08:00" |

## 7. 异常场景处理矩阵

| 异常场景 | 表现 | 处理策略 |
|---------|------|---------|
| APK下载未完成即启动App | 下载进度 < 100% | 清除未完成文件，重新下载 |
| APK下载后MD5校验失败 | 文件损坏 | 转至"更新失败"页面，显示"文件校验失败" |
| 存储空间不足 | 无法写入/安装 | 转至失败页，错误描述"存储空间不足" |
| 安装过程被系统拦截 | 安装失败 | 转至失败页，错误码匹配系统返回的错误 |
| 网络中断（下载阶段） | 下载暂停 | 恢复网络后自动续传（不限速） |
| 取消更新后重新启动 | 进入App | 清除标记——不对，取消后下次启动仍触发更新 |
| 点击"开始更新"后立即关机 | 更新未执行 | 下次启动重新检测→校验→触发 |

## 8. 灰度发布策略（推荐）

| 阶段 | 分发比例 | 观察期 | 验收标准 |
|------|---------|--------|---------|
| 内部验证 | 指定白名单设备 | 1天 | 无安装失败 |
| 小范围灰度 | 5%（按deviceId哈希） | 2天 | Crash率 < 0.1%，安装成功率 > 99% |
| 中范围灰度 | 30% | 2天 | Crash率 < 0.1%，无功能异常反馈 |
| 全量发布 | 100% | - | 持续监控3天 |

灰度策略按设备ID哈希取模实现，同一设备始终落在同一灰度桶内，避免反复横跳。

建议灰度期间在运维后台实时展示：`上线设备数 / 总目标设备数` 和 `安装成功率 / 失败率`。
