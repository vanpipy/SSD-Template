# Prompt: 原始需求 → PRD

## 你的任务

读取指定的原始需求文件,按照 `schema/prd.md` 的格式,产出一个或多个符合规范的 PRD 文件。

## 输入

```
原始文件夹: prd/{YYYY-MM-DD}/         ← 包含原始需求文件的文件夹（批量处理）
输出文件夹: prd/{YYYY-MM-DD}-processed/   ← 固定命名：{原始文件夹名称}-processed
```

读取文件夹内所有 `.md` 文件作为原始输入，统一产出到同一个 `-processed` 文件夹下。

## 执行步骤

### 第一步: 读取并理解原始文件

读取所有相关原始文件(PRD、流程图、会议纪要、技术方案等),理解:
- 这个功能要解决什么业务问题
- 涉及哪些用户角色
- 包含哪些核心流程和异常路径

### 第二步: 确定拆分粒度

**原则: 一个 PRD = 一个独立可交付的功能单元**

- 如果原始文件只描述一个功能 → 产出一个 PRD
- 如果原始文件包含多个功能模块 → 每个核心流程单独产出一个 PRD
- 判断依据: 这个功能可以独立上线、独立验收吗?

### 第三步: 提炼各字段

**Why — 问"这个功能为什么存在"**
- 从业务背景、产品定位、用户痛点中提取
- 必须是一句话: 这个 PRD 是为了 [问题] 而存在,期望达成 [目的]

**Goal — 问"交付什么可验证的结果"**
- 从功能清单、验收标准中提取
- 每条必须可观察/可测量
- 禁止: "支持 XX"、"完成 XX" 等模糊描述
- 正确示例: "用户输入手机号后,系统在 2s 内返回会员信息或提示不存在"

**Scenarios — 将流程转为 Given/When/Then**
- 流程图的每条主路径 → 一个正常场景
- 每个异常分支 → 一个异常场景(至少保留一个)
- 格式:
  ```
  Given [用户所处状态 + 前置条件]
  When  [用户执行的动作]
  Then  [系统返回的可验证结果]
  But   [异常时的处理](有异常分支时填写)
  ```
- Then 必须具体: 返回什么数据、跳转到哪个页面、触发什么状态变更

**Out of Scope — 明确不做什么**
- 原始文件中标注"框架阶段"、"后续迭代"的模块
- 依赖外部系统但不在本次交付范围的能力
- 至少写 2 条

### 第四步: 按模板产出文件

参考 `schema/prd.md`,填写所有必填字段:
- 状态设为 `Active`（内容已提炼完整，可进入 Tech Design 阶段）
- 负责人填写已知信息,未知则填 `TBD`
- 复审字段填写当前日期,答案暂填 `Yes`
- Links 中填写本文件路径和预期的 tech_design/plan 路径

> 说明：`Draft` 表示内容尚未完整；本流程产出时内容已经过提炼，直接设为 `Active`。

### 第五步: 检查完成门

产出前逐项确认:

- [ ] **为什么** 用一句话具体问题陈述回答
- [ ] **目标** 每条都可观察/可测量,无模糊描述
- [ ] **场景** 覆盖正常路径 + 至少一个异常
- [ ] **不在范围** 至少 2 条,明确说明
- [ ] **复审** 已填写

## 输出格式

产出目录命名规则：`{原始文件夹名称}-processed`

```
prd/{原始文件夹名称}-processed/
├── {topic-a}.md    ← 功能单元 A
├── {topic-b}.md    ← 功能单元 B (如有拆分)
└── ...
```

每个文件严格按照 `schema/prd.md` 结构,不添加 schema 之外的章节。
