## 2. 流程拓扑:主干是**人串行**,agent 只在层内

### 2.1 主干的闸门序列【事实】

`HOW_TO_USE.md:182-193` 的 5 步工作流图 + `HOW_TO_USE.md:318-326` 的转换触发表,合并起来是:

```
Step 0 素材 ──Step1──> PRD ──Step2──> Tech Design ──Step3──> Plan ──Step4──> 外部代码仓 TDD
                        │Gate1          │Gate2                │Gate3              │Gate4
                        ▼                ▼                     ▼                   ▼
                    人填复审三行    人填复审三行          人填复审三行      人回写三件套 Implemented
```

- **Gate 1/2/3**:人工在 `## 复审 (Review)` 段填 `> **评审人**` / `> **评审日期**` / `> **评审结论**` 三行(`HOW_TO_USE.md:328-339`)。
- **Gate 4**:外部 PR merged 后**人工回写 wiki 三件套 Implemented**。`HOW_TO_USE.md:324` 的校验命令栏原文写着「人工检查外部仓库(**无脚本**)」,责任方栏写「外部 reviewer + wiki 人工回写」。
- 可选层 Test Cases 另有两道:`Draft→Ready` 复审一道,`test-done → Implemented` 一道(`sync-status/SKILL.md:68`:「**独立生命周期**:冒烟/全量执行通过后单独回写 `Implemented`」)。

⇒ **主干 4 道人工闸门;开测试用例则 6 道。**

### 2.2 推论:agent 的产能被**复审速率**封顶【推断】

- agent 的权限天花板是 `Draft`(`schema/prd.md:9`「agent 可写上限 = `Draft`」;四个产出类 skill 的 description 逐字写着「agent 只能产出 Draft 状态, Ready 与 Implemented 由人工写入」;`sync-status/SKILL.md:6`「状态判定权归人, agent 只在人工明确指定转换后执行写入」)。
- 一次特性里 agent 能做的全部工作 = Step 1~3 的正文。它做完也**解锁不了**下一层,因为解锁权在复审者手里。
- ⇒ **任意时刻,一个特性的 agent 工作量上限 = 一次复审周期**。加 agent 不会缩短链路,只会把"等复审"之前的堆料时间变短。

这条推论直接决定:SDD 的吞吐优化点**不在 agent 侧**,在**复审侧**(见 §8)。

### 2.3 复审者实际拿到的东西

复审者是唯一的内容把关者,但复审时手上的文档:

- 机器**已**保证:段齐全、状态枚举合法、占位符清零、编号闭环、被引路径存在。
- 机器**没**保证:任何一条主张为真。

⇒ 复审者必须**从零验证**一份机器只验过形状的文档。这决定了 §3.4 的改造方向。

### 3.4 唯二现成的「人机共用裁决载体」都没被用作裁决

PRD 的 `## 目标` 是**勾选项列表**(`schema/prd.md:27-28`,形如 `- [ ] 验证标准 1`),`## 复审` 下半是**固定三问表**(`schema/prd.md:82-86`:仍然重要? / 应当保留? / 可以删除?),`schema/prd.md:74` 要求「两者都要填真日期」。

【事实】脚本对这两样**零校验**:
- `check-md-schema.sh:381` 只检查 `## 目标` 段**含至少一个 `- [ ]`**,不检查复审后是否被勾上;
- 全 `scripts/` 目录 grep `still_matters|should_keep|can_delete|\[x\]|勾选` → **只命中 `check-md-schema.sh:381` 一行**(且是"有没有勾选项"这一句)。

⇒ 【推断】流程里已经存在"逐条可裁决"的天然载体(可勾选的标准 + 固定三问),但机器不读它们,人也不被要求在其中留下裁决痕迹。复审三行只记录**谁签了**,不记录**签的是哪一条**。
⇒ 推论:要把内容层从"全靠人"改成"人机共担",**成本最低的落点就在这两个已有结构里**,不需要新造格式。

## 4. 十个断点

每条:现象 → 证据 → 后果 → 现有兜底 → 谁能补。

### B-1 上游必须 `Ready` —— 唯一有全局顺序含义的规则,机器零覆盖

- **现象**:规则只以散文形式存在两处 —— `HOW_TO_USE.md:224`「基于状态为 `Ready` 的 PRD,产出…」、`HOW_TO_USE.md:244`「基于状态为 `Ready` 的 Tech Design,产出…」;另有 `WORKFLOW.md:302` 给 agent 的 prompt 义务。
- **证据**【事实】:`scripts/` 全目录唯一的跨层状态比较是 `Deprecated` 级联(`check-traceability.sh:543`/`:553`/`:571`)。`Ready` 在 `check-md-schema.sh:324-347` 只校验**本制品自己**的复审三行,从不读上游状态。
- **实测反证**【事实】:临时副本上 `Draft PRD → Draft TD → Draft Plan → Draft TC` 全链 5 个门禁**全 exit 0**(副本已删);把上游改成 `Deprecated` → 级联报错 exit 1 ⇒ 脚本**读得到**上游状态,只是**没做** Ready 判定。
- **后果**:agent 在上游还没复审时写下游,机器全绿。
- **兜底**:只有 agent 读 prompt 时的自觉。
- **谁能补**:**编排层**(派发前算依赖)或**产物层**(下游声明上游状态并被校验)。取舍见 `operation-flow.md` §12.1。

### B-2 PRD → TD 的连接强度只有「行数」

- `check-traceability.sh:527`:场景映射表**行数** ≥ PRD 场景数,否则报错。**不校验哪一行对应哪个场景,也不校验映射内容。**
- **后果**:TD 可以写 N 行无关内容通过检查;PRD 场景 ↔ TD 场景映射的**语义对应**是纯人工。

### B-3 `## 跨文件引用对账` 是自报产物

- `check-md-schema.sh:483` 只要求该段存在;`check-traceability.sh:462`/`:474-475` 只做 `### Change #N:` ↔ `### V-{n}:` 的**编号闭环**。
- **后果**:对账表里「Plan Change ↔ 上游 TD KD ↔ 测试用例」的映射主张**没有任何一条被机器验证**。这是 Plan 层唯一的跨层对齐声明,却是自报。

### B-4 Plan → 代码:没有任何映射

- TD 的 `## 实现基线`(`check-repo-baseline.sh` 全文)是**代码状态快照**(仓库 | 分支 | SHA | 核对日期 | 核对项 | 状态),不是「Plan Change → 代码 commit」的映射。
- **后果**【事实】:SDD 里**没有"这个 Change 落地了没有"的机器可查答案**。实现回写链 100% 人工。

### B-5 `Implemented` 终态没有外部事实源

- `HOW_TO_USE.md:324` 校验命令栏原文:「人工检查外部仓库(无脚本)」。
- **后果**:流程的终点状态是纯人工断言;而 `HOW_TO_USE.md:341-343` 又要求三件套**同时**进 Implemented ⇒ 一次外部事实要在 3 个文件里各写一遍,且**没有任何东西校验这 3 次写的内容一致**(`sync-prd.sh` 只统计各层状态分布,不比对三件套是否同步)。

### B-6 复审三问(防 feature rot)无人校验

- `schema/prd.md:82-86` 定义三问表,`schema/prd.md:74` 要求「两者都要填真日期」;脚本零校验(§3.4)。
- **后果**:周期性复审是**流程里最容易被静默跳过的环节** —— 它既不进门禁,也不影响任何状态机,跳过了没有任何红灯。

### B-7 验证标准是勾选项,但勾选没有语义

- `schema/prd.md:27-28` 的 `- [ ] 验证标准 N` 是 PRD 质量的唯一可操作锚点;`check-md-schema.sh:381` 只查"有没有"。
- **后果**:复审者可以在**不逐条裁决**的情况下签署,而流程没有任何地方记录哪些标准被确认过。

### B-8 台账里的状态是制品状态的影子副本,两者互不校验

- `schema/prd-ledger.md:35` 明写台账 `状态` 列取值 = `待分析` + 四态,并注明「`待分析` 是**台账哨兵**,不是层生命周期状态」。
- 但 `check-traceability.sh:325-336` 的 `node_state()` **优先读台账状态**,只有当节点用**路径**标识时才回退读制品状态行。
- **后果**:同一个 PRD,制品状态行写 `Deprecated`、台账状态列还写 `Ready` 时,用台账 ID 标识的关系边会按 `Ready` 判定 ⇒ `T8` supersede 一致性(`:380`/`:395`)用错状态。
- **范围**:T12 级联(读父制品路径)不受影响;受影响的是**关系边节点**。

### B-9 台账完整性是单向的

- `check-traceability.sh:295-312` 只查台账 ID 格式与唯一性;**不查"每个 PRD 是否都登记了"**。
- `sync-prd.sh:291` 的「孤儿行」= 台账行指向的素材不存在(**反向**);`:325`「台账有未标记的待办行」是 err;`:354`「批次台账缺失(该批次素材未登记)」是 err。
- **后果**:未登记的 PRD 永远不会被发现;而台账只覆盖 `material/` 启用场景(可选层,默认不启用)。

### B-10 索引 / 统计层一文件两写者

- 根 `README.md`:人维护全文 + `sync-prd.sh:444-453` 写 `<!-- prd-stats:begin -->`…`end` 块(缺块 → err)。
- `material/{date}/PRDS.md`:`sync-prd.sh:352-363` 建骨架 + `:390` 写入待分析哨兵,人填内容。
- `test_cases/_index.md`:`sync-test-index.sh` 唯一机器写者(干净)。
- `prd/README.md` / `tech_design/README.md` / `plan/README.md` / `material/README.md`:**纯人工**,与 `_index.md` 不对称。
- **后果**:不一致时没有权威源裁决;但影响面小(只影响导航与统计,不影响任何门禁判定)。

## 6. 状态的两个权威源

【事实】SDD 状态有**两个可写位置**:

| 载体 | 写入者 | 机器在哪读 |
|---|---|---|
| 制品内 `> **状态**: X` | 人(agent 到 Draft 为止) | `check-md-schema.sh:241-252`(本制品)、`check-traceability.sh:543`/`:553`/`:571`(级联,读父制品路径) |
| 台账 `状态` 列 | 人 / `sync-prd.sh` 哨兵 | `check-traceability.sh:318`(收集 Deprecated)、`:328`(`node_state()` **优先读**) |
| README 统计块 | `sync-prd.sh`(只读制品态) | 人 |

⇒ 真正的权威源是**制品内的状态行**(台账是影子副本);但 `node_state()` 的优先级让台账在关系边场景里**反客为主**。B-8 就是这条反客为主的代价。

## 7. 结构性结论

1. **SDD 是"人串行 + agent 层内"的流程,不是 agent 流水线。** 主干 4 道人工闸门串行,agent 的天花板是 Draft ⇒ 吞吐瓶颈在复审侧,不在 agent 侧。
2. **83 条断言里没有一条断言内容。** 门禁保证的是"可评审",不是"对"。这是**设计上的诚实**(`HOW_TO_USE.md:312-316` 明写),但代价是质量保证 100% 压在 4 次人工复审上。
3. **跨层连接比看上去弱得多。** PRD→TD 只有行数,TD→Plan 只有编号存在,Plan→测试只有路径,Plan→代码**完全没有**。⇒ 在机器眼里,这三层是**三堆独立文档**,不是一条链。
4. **唯一有全局顺序含义的规则(上游 Ready)恰好是唯一零机器覆盖的规则。** 越重要的规则,越没有机器背书。
5. **人机共担的载体已经现成,但没人用。** 勾选式验证标准 + 三问复审表是流程里唯二"逐条可裁决"的结构,机器不读、人不被要求留痕。⇒ 内容层改造的最低成本落点在这里,不必新造格式。
6. **状态有两个权威源,且机器读的不一致。** 制品状态行是真相,台账是影子,`node_state()` 在关系边场景优先读影子(B-8)。
7. **流程闭环于文档,不闭环于代码。** `Implemented` 靠人回写且要三处各写一遍,无一致性校验(B-5);Plan→代码无映射(B-4)。
