# Step 3: Analyzing Phase

从输入文档提取功能点，匹配知识库，向用户确认。

> **核心原则**：源文档只读取一次，提取结果写入工作上下文，后续 Step 4/5/6 仅引用提取结果，不重读源文档。

## 提取来源

### From PRD

| 段落 | 提取内容 |
|------|---------|
| Scenarios（Given/When/Then/**But**）| 功能场景清单；**But 子句单独提取为异常/边界分支清单，先 `grep -c '\*\*But\*\*'` 计数，一条不许丢（v2.3）** |
| Goal | 验收标准 + **显式默认值（初始状态验证点，如总开关默认开/音量默认 60）(v2.3)** |
| Out of Scope | 负面测试边界（不测什么）|

### From Tech Design

> v4 TD 为 4 子文件 (README/apis/ards/data-model)；存量 v3 TD 用括号内旧文件名。

| 文件 | 提取内容 |
|------|---------|
| README.md「场景映射」段 | 技术场景映射（**But 映射行逐条对照 PRD But 清单**）（存量 v3：`scenario-mapping.md`）|
| `apis.md` | 接口参数边界（入参/出参/错误码/全响应变体）（存量 v3：`api-contracts.md`）|
| `ards.md` | 技术约束 KD（推导隐含边界）+ **OQ 清单——收敛方式点名测试用例的（如离线冒烟）= 必须生成的用例 (v2.3)**（存量 v3：`decisions.md` + `exploration.md`）|
| README.md「质量保证」段 | 性能/安全要求 + **降级策略（D{n}，每个降级都要有触发用例）(v2.3)**（存量 v3：`quality.md`）|
| `data-model.md` | 数据模型约束（字段长度/类型/关联/ER 图实体关系）|

### From 业务模板（若存在）

- `test-business/{product}/_rules.md` → 已有业务规则
- 已有 YAML 用例 → 避免重复、保持风格一致

## 功能点清单输出

提取后向用户展示表格，**必须等用户确认后才继续**：

```
我提取到以下功能点，请确认或补充：

| # | 功能点 | 来源 | 关键程度 | 使用频率 | 建议用例数 |
|---|--------|------|---------|---------|-----------|
| 1 | 手机号登录 | PRD-S1 | 关键 | 高频 | 8 |
| 2 | 验证码校验 | PRD-S2 | 重要 | 高频 | 6 |
| 3 | 生物识别登录 | TD-KD3 | 重要 | 中频 | 5 |
| ...

是否需要：
1. 补充功能点？
2. 调整关键程度/使用频率？
3. 删除不需要的功能点？
4. 确认进入生成阶段？
```

## 关键程度推导

- PRD Goal 中的核心功能描述 → **关键**
- Tech Design ards.md 提到的数据一致性要求（存量 v3：decisions.md）→ **关键**
- 涉及资金/交易/数据正确性 → **关键**
- 功能完整性/状态一致性 → **重要**
- 体验/展示/辅助 → **一般**

## 使用频率推导

- Scenarios 中出现次数多、多个场景共享的步骤 → **高频**
- 主路径上的步骤 → **高频**
- 仅特定分支才走到的路径 → **低频**
- 管理后台/配置类操作 → **低频**

## 信息缺口处理

若 PRD/TD 信息不完整：
- 标注假设（如"假设验证码有效期为 5 分钟"）
- 在功能点清单中注明"待确认"
- 不阻塞流程，但记录在输出中

## 输出

```
✅ 功能点确认完成：共 N 个功能点
- 关键：N 个
- 重要：N 个
- 一般：N 个
- 信息缺口：N 项（已标注假设）

→ 进入 Step 4: Generating
```
